# WP-TRG-040: Three-Case Hosted Closed-Loop Evaluation

- Status: deferred
- Owner: unassigned
- Reviewer: independent reviewer required
- Risk tier: G3

## Entry condition

TRG-039 is completed and independently reviewed, its release/dossier hashes
remain unchanged, and the user selects this workpack. The activation package
must cite M155, `WP-TRG-035`, the frozen TRG-039 release record and provider
runbook. Before provider construction it must complete hosted preflight and
obtain fresh itemized user authorization.

## Goal

Run one finite development-only, three-case real-provider evaluation of the
frozen closed-loop release, producing attributable terminal evidence rather
than a general CAD benchmark or card-effect claim.

## Scope

- Execute exactly frozen `cylinder`, `block_with_hole`, and `three_hole_plate`
  development cases, in frozen order, with no substitution or held-out use.
- Revalidate input/split/card/index/release hashes, provider/model, path-free
  outbound schema, executor, tool/repair limits, deadline, request ceiling and
  fresh distinct report/monitor paths before authorization.
- Issue only the frozen loop: bounded Q01 tools, one explicit selected card,
  initial script, restricted execution/gates and at most one M141
  `source_only` repair when eligible. All other classes remain zero-repair.
- Preserve sanitized evidence for tool compliance, card hash/role consistency,
  first-pass and gate stages, classification, repair eligibility/attempt/
  conversion, request count, duration and terminal reason.
- Complete independent terminal review. Interpret the denominator as exactly
  these three development cases; publish no generic, held-out, cross-family,
  generic-repair or card-effect conclusion.

## Attribution question and sampling intent

Determine whether a real provider can complete the exact frozen
observation/card/generation/execution/classified-repair loop with attributable
terminal evidence on three direct-evidence development roles. The information
gain is lifecycle and repair observability, not efficacy estimation. Stop on
boundary drift, authorization absence, integrity failure, or each predefined
case terminal; failure never permits added cases, changed prompt/card/Harness,
retry or budget reuse.

## Decision-package impact

- `decision_id`: none; finite hosted release evaluation.
- Q01/Q02 effect: measures frozen interfaces only; no new claim.
- Q03/Q04 effect: records existing gates/classification; no policy widening.
- Evidence role: development-only hosted lifecycle/regression evidence.
- Knowledge disposition: review may record one source-linked counterexample or
  no reusable knowledge; neither authorizes promotion.

## Authorization requirements

Fresh authorization must name destination, provider/model, three case IDs and
hashes, path-free outbound content, card/index hashes and roles, maximum tool
turns and repair rounds, deadline, maximum request/cost budget, no-input
executor, and new report/monitor paths. The activation package calculates the
exact maximum completion count from TRG-039's frozen per-case bound: at most
four provider completions per case, hence at most twelve for the campaign.

## Compatibility constraints

No raw STEP, local path, reference script, held-out answer, arbitrary repo
content, credential, full provider response or directory retrieval leaves the
Harness. One hosted campaign is active at a time. Historical M135 reports,
capacity and authorization cannot be reused.

## Acceptance

Record local preflight, independent G3 review, explicit authorization,
terminal report/monitor evidence, relevant tests/Ruff/governance audit and a
terminal evidence review.

## Out of scope

Additional cases/batches, held-out evaluation, baseline/treatment comparison,
model/prompt comparison, retries, new repair types, card mutation, retrieval,
training, manifest changes or Harness changes during the campaign.
