# Current Hosted Evaluation Framing

This document defines the current wording for Brep2Code's hosted evaluation
scope. It does not replace the four-track roadmap, activate a workpack, alter
case/card/runtime authority, or authorize a provider request. It is a framing
layer for current evaluation work so historical route documents do not become
selection noise.

## Purpose

At the current stage, Brep2Code is not trying to answer whether an LLM can
perform generic CAD modeling in the large. The bounded question is:

> Under a frozen Harness boundary, fixed case scope, finite observed facts, and
> explicitly limited reference material, can a hosted LLM complete a specific
> B-Rep-to-CAD task path with attributable terminal evidence?

Hosted results support only the bounded claim named by their frozen policy.
They do not establish a model benchmark, generic reconstruction ability,
feature-history recovery, or broad CAD generalization.

## Relationship to the four tracks

The four tracks remain the project routing authority:

1. hosted stability;
2. reference-assisted construction;
3. reference-guided parameter variation; and
4. modeling-sequence coverage.

This framing does not replace those tracks. It states how to interpret the
current hosted-evaluation phase that sits on top of them:

- hosted stability remains the prerequisite route for trustworthy provider-side
  lifecycle and script/execution evidence;
- reference-assisted construction asks whether a bounded derived card can help
  reconstruct one declared mechanism role;
- reference-guided parameter variation asks whether finite observations plus
  one declared action card can support a bounded comparison on unseen parameter
  combinations; and
- modeling-sequence coverage supplies the family-scoped mechanism portfolio
  that may later receive hosted campaigns.

Historical route documents remain background evidence unless the active
workpack explicitly names them.

## Current selection rule

M134's existing-case development epoch was executed as M135-011, then received
M137 terminal evidence review; M138 added only content-safe observability for
future static API rejections. Those completed records are terminal evidence,
not reusable hosted capacity. The M139/M140/M141 launcher, tool-loop and
classified-repair contracts are already complete offline, and the M142--M157
authority-and-entry-boundary plus governed-case contract-alignment prelude is
also complete. The current recommended planning order before any new provider
campaign is to separately select `WP-TRG-039` for an offline three-case
closed-loop release freeze against M139/M140/M141, then select `WP-TRG-040`
only after independent closure. The latter remains G3 and requires fresh
preflight and itemized authorization. Its independently reviewed terminal
evidence may then support the offline TRG-041 decision on one repair-attempt or
interaction-budget successor; it does not itself widen the frozen campaign.

## Finite case scope

`Finite case scope` means a predeclared, auditable, non-substitutable case set.
It is not an informal small sample.

Three bounded campaign shapes are allowed:

1. **Single-case smoke**: one fixed case answers whether one declared path can
   complete end to end under the frozen boundary.
2. **Single-family development campaign**: one frozen family/split answers a
   development-side mechanism question under a fixed policy.
3. **Single-family held-out campaign**: one separately frozen held-out family
   split tests the same bounded question only after development-side evidence
   is interpretable.

Finite case scope therefore requires all of the following before hosted use:

- fixed case IDs or family rows;
- fixed split membership and order;
- fixed stopping rule and denominator;
- no replacement case after a terminal failure; and
- no interpretation that exceeds that frozen denominator.

## Limited reference scope

`Limited reference scope` means only predeclared, hash-bound, role-scoped
materials may assist the model.

Allowed reference forms:

- bounded observed facts from Q01;
- one declared reference pack or runtime card whose status is already fixed;
- one declared action/API contract; and
- compact counterexample or applicability metadata already admitted by policy.

Disallowed reference forms:

- raw STEP or other raw input geometry;
- local paths, filenames, or workspace-only identifiers;
- full reference scripts or reference answers;
- post-result card edits or answer-guided prompt changes; and
- broad retrieval merely because a case has a script, case card, or pack.

In this phase, `human case cards`, `development reference packs`, and
`runtime experience cards` remain distinct authorities. One does not imply the
others.

## What each current question validates

### Reference-assisted construction

This track validates whether a derived, role-scoped construction card can help
the model produce a valid script for one declared mechanism role without source
answer leakage.

Its hosted evidence may support:

- one fixed case or one later frozen family campaign;
- one declared role/card boundary; and
- one bounded interpretation of terminal pass/failure.

It may not support:

- broad card promotion;
- generic mechanism competence;
- quality claims across unrelated roles; or
- automatic transition from a successful smoke to wider sampling.

### Reference-guided parameter variation

This track validates whether finite observed facts plus one declared action
card can support a bounded comparison on unseen parameter combinations without
reference-answer leakage.

Its hosted evidence may support:

- one frozen development-only comparison;
- later, a separately frozen held-out comparison if the policy remains
  interpretable; and
- one bounded conclusion about the predeclared comparison question.

It may not support:

- generic parameter generalization;
- card-effect estimation from an uninterpretable baseline failure;
- held-out authorization by analogy to development success; or
- reuse of a prior development budget, report, or policy.

### Five-family mechanism portfolio

The five-family route does not ask whether one card helps. It asks whether
representative CAD mechanism families can each accumulate a family-scoped,
reviewable hosted evidence path under the observation-first Harness boundary.

Its current portfolio question is:

> For one frozen mechanism family at a time, can the observation-only Harness
> support an independently reconstructed result under that family's fixed
> policy and existing execution/gate boundary?

Accordingly:

- the five families are a mechanism-coverage portfolio, not a card-effect
  portfolio;
- prismatic cylindrical cut remains a special case because its current hosted
  interpretation depends on the separate parameter-variation policy route; and
- the other four families are currently no-card candidates, so a future hosted
  campaign would validate a bounded no-card mechanism question rather than a
  runtime-card effect.

## What hosted evaluation must cover

Hosted evaluation exists to cover evidence that offline replay cannot supply.
Each hosted campaign must preserve separate records for:

- provider lifecycle and request accounting;
- generated script/API admissibility;
- secure executor and sandbox/provenance outcome;
- output and geometry/semantic/editability gates that actually ran; and
- the one allowed interpretation named by the frozen policy.

Hosted evaluation should not be used to:

- repair an under-specified policy by adding more samples;
- merge timeout, API failure, geometry failure, and semantic failure into one
  capability score;
- infer a global success rate across different policies; or
- treat replay success alone as hosted readiness.

## Current-phase campaign discipline

For the current phase, campaign preparation follows this order:

1. finish the applicable offline dossier, family freeze/release, or card
   qualification boundary;
2. freeze one campaign charter: question, scope, split, references, request
   accounting, gates, and stop rule;
3. complete hosted-stability prerequisites and the campaign-specific preflight;
4. run one development campaign with fresh report/monitor paths;
5. perform independent terminal review before any follow-on selection; and
6. only then consider a separately selected held-out campaign.

`Batch hosted evaluation` in this phase means one pre-registered cohort of
independent family conditions under an unchanged execution boundary. Serial
issuance is allowed for budget and monitoring, but one condition's terminal
failure does not gate another condition. An integrity failure of the frozen
boundary is the only epoch-level stop. It does not mean opening the whole case
library or aggregating heterogeneous reports into a benchmark.

The M134 cohort is completed historical evidence.  It cannot be resumed,
repaired in place, used to alter a card, or treated as a pre-authorized basis
for a later campaign.

Only one hosted campaign may be active at a time. Historical campaigns remain
bounded terminal evidence; they do not become reusable capacity or implicit
green lights for the next family.

## Current non-goals

This framing explicitly does not authorize:

- replacing the four-track route with one aggregate hosted program;
- reviving old route candidates by search hit alone;
- broadening from finite cases to an open case-library batch;
- treating case-card completion as runtime-card readiness; or
- claiming project-level capability from portfolio counts.
