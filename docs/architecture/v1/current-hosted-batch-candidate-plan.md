# Current Hosted Batch Candidate Plan

This page translates the current hosted-evaluation framing into a practical
next-phase candidate plan. It does not replace the four-track roadmap, select a
workpack, or authorize a provider request. Its purpose is narrower:

1. identify which families are currently blocked only by shared hosted gates;
2. identify which families still need family-specific offline work before they
   can become hosted candidates; and
3. define a low-noise first batch sequence once the shared prerequisites are
   satisfied.

## Scope of this plan

`Batch` means a scheduled sequence of independently frozen hosted campaigns.
Each campaign still needs its own workpack, preflight, authorization, report
path, monitor path, and terminal review. This page only identifies readiness
and ordering.

## Shared prerequisite gates

Every five-family campaign remains blocked by the same shared route until the
post-M129 hosted-stability path is re-opened and passes its current gate. That
shared route is not family-specific offline evidence, but it is a hard
prerequisite for every later campaign.

M135-011 completed M134's 18-condition development epoch with reviewed,
mixed condition terminals.  It did not establish a shared full downstream-gate
pass, a card effect, or reusable hosted capacity.  The shared prerequisites for
any later family campaign therefore remain: a newly selected G3 package,
fresh offline preflight, explicit itemized authorization, one active campaign
at a time, and independent terminal review.  The earlier offline
`WP-TRG-024` through `WP-TRG-028` sequence is no longer the current next-step
plan: M139/M140/M141 and the later M142--M157 authority/entry-boundary and
governed-case contract-alignment prelude are already complete. The project-level
route first freezes and evaluates the three-case closed loop through TRG-039
and TRG-040, then reviews repair/interaction policy through TRG-041. This plan
remains a future family-governance view; it cannot select a family campaign or
replace the current route.

## What must still be done offline

The offline work now splits into two categories.

### A. Shared offline work before any batch

This work is not family-specific, but it still must happen before the batch:

1. independently review M134's frozen batch policy;
2. complete selected M136 offline remediation, then a fresh M135 preflight and
   itemized authorization; and
3. execute without mid-epoch modification, then select M137 for terminal
   review.

### B. Family-specific offline work

No family needs additional mechanism design or charter-freeze work for the
completed M134 epoch.  For a future campaign, a newly selected workpack must
freeze its own facts without changing historical M134 evidence:

- define one exact no-card question for the selected family;
- map that question to one fixed family split and one exact Q01 egress
  contract;
- define one family-specific interpretation table that keeps lifecycle,
  script/API, sandbox/provenance, and downstream gates separate; and
- record one allowed conclusion and one explicit non-inference for that family.

For **repeated feature pattern**, M123 has already drafted the bounded no-card
development campaign charter. Any later G3 work must carry that charter
forward unchanged or explicitly supersede it with a fresh frozen boundary.

For **axisymmetric revolve**, M124 has already drafted the bounded no-card
development campaign charter. Any later G3 work must carry that charter
forward unchanged or explicitly supersede it with a fresh frozen boundary.

For **dependent face selection**, M125 has already drafted the bounded no-card
development campaign charter. Any later G3 work must carry that charter
forward unchanged or explicitly supersede it with a fresh frozen boundary.

For **multi-inner-loop pocket**, M126 has already drafted the bounded no-card
development campaign charter. Any later G3 work must carry that charter
forward unchanged or explicitly supersede it with a fresh frozen boundary.

For **prismatic cylindrical cut**, M120 has already drafted the bounded
development campaign charter. Any later G3 work must use the reviewed M115
development-only successor policy rather than the obsolete M97 held-out
interpretation.

## Frozen first-batch epoch

M134 freezes the following issuance sequence under one unchanged policy:

1. **Repeated feature pattern**
2. **Axisymmetric revolve**
3. **Dependent face selection**
4. **Multi-inner-loop pocket**
5. **Prismatic cylindrical cut** with the M120/M115 frozen card/no-card
   development conditions

This order is recommended for current planning because:

- the first four are already family-complete and need no new mechanism
  evidence;
- all four are explicitly no-card candidates, so they avoid mixing runtime-card
  promotion with family hosted evidence;
- repeated pattern and revolve offer tightly frozen whole-family questions with
  simple family-level denominators;
- dependent face selection adds selector dependency after the simpler fixed-role
  families;
- multi-inner-loop pocket adds the most role-structured Q01/Q02 coupling among
  the currently family-complete no-card candidates; and
- prismatic retains its predeclared paired interpretation and cannot support a
  held-out or generalization claim.

This is a frozen observation order, not a causal gate. A terminal case-level
failure is recorded and the next condition continues unchanged. Only the M134
epoch-integrity stop rules may stop issuance; no repair is inserted.

## Epoch admission trigger

Every family above is admitted to the same M134 epoch. M135 must validate the
complete cohort and cannot drop, add, replace, or reorder a condition after
authorization.

## Deferred options

Native-shell evidence, robustness micro-families, additional reference-assisted
qualifications, held-out parameter variation, and any post-epoch campaign are
deferred. M136 remediation, re-entered M135, and M137 review are the only
successors of M134; none changes case
authority or authorizes provider use before G3 preflight and itemized approval.

## Adaptive slack

The preparation queue should keep limited adjustment headroom without reopening
policy scope:

- Prepared line: repeated feature pattern through completed M123
- Prepared line: axisymmetric revolve through completed M124
- Prepared line: dependent face selection through completed M125
- Prepared line: multi-inner-loop pocket through completed M126
- Primary queue: none
- Reserve queue: none
- Separate prepared line: prismatic through M120 under M115

If a later hosted slot opens and one prepared family is blocked by a missing
family-local prerequisite, switch to the next prepared family in the queue.
Do not revise the frozen charter of the skipped family inside that switch.

## What is not needed now

The current records do **not** support doing any of the following as a default
next step:

- broadening to open multi-family hosted sampling;
- adding new runtime cards for the four no-card families before asking their
  hosted family questions;
- using prismatic development evidence as if it already answered a held-out or
  generalization question; or
- selecting `shell` or `rib` for hosted work before the five-family portfolio
  has usable reviewed hosted evidence.
