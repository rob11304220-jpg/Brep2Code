# Current Project Route: Auditable Hosted Closed Loop

## Project-level objective

The current project objective is to obtain attributable hosted evidence for a
real LLM completing a **frozen, bounded B-Rep-to-CAD closed loop**:

```text
bounded Q01 observation + one explicit reference card
  -> script generation -> restricted execution and gates
  -> classified feedback -> only an admitted bounded repair
  -> terminal report and independent review
```

This is not a claim of general B-Rep reconstruction, generic CAD repair, card
utility, or a benchmark. `docs/workflow/status.md` remains the authority for
which workpack can be selected now; this page gives the stable project-level
meaning of that selection.

The planned 30-case denominator has three predeclared strata of ten cases:
Q01-only/no-card/no-repair; Q01 plus one explicit card/no-repair; and the full
bounded Q01/card/generation/gate/classified-repair loop. Report terminal-gate
and first-pass rates, repair eligibility/conversion/plateau, tool/card
compliance, completion use, duration, failure classes and Wilson intervals.
Different strata are not a causal card comparison.

M172's equal-strata charter is historical provenance only. M174's selected
[asymmetric hosted denominator charter](../../workflow/m174-asymmetric-hosted-denominator-charter.md)
is the binding interpretation: a 30-case no-card main cohort plus an unpooled
three-role card-assisted feasibility annex. M175 is the fresh G2 qualification
ledger for those revised denominators; campaign freeze cannot be claimed
automatically.

Unexpected feedback requires a newly scoped, explicitly user-selected workpack
with an uncertainty, counterexample, stop rule and re-entry point. After it
closes, resume at the next unmet gate. A reproducible blocker that cannot be
resolved marks the route blocked. The G3 step always stops after fresh preflight
and independent review until itemized authorization covers provider/model,
cases, egress, deadline, completion/cost ceiling, executor and fresh report
paths.

## Supporting routes

### 1. Repair and Harness interaction policy

The Harness is a fixed safety and observability substrate; campaign policy
freezes the permitted tool calls, response sizes, completion budget, repair
classes and per-class attempt caps. The initial release is deliberately small:
one declared Q01 call, one explicit card call, one initial script and at most
one `source_only` edit. This is a baseline for measuring conversion and plateau,
not the permanent optimal configuration.

M141 is the current implementation authority. Its source-level classes may use
one edit; selector ambiguity, geometry/semantic, editability, sandbox/
provenance, timeout and provider/protocol outcomes stop fail-closed. Future
evolution is evidence gated:

- retain the baseline if evidence is insufficient;
- test one additional `execution_local` source edit only after a changed
  normalized failure signature; or
- create a separate prerequisite route for geometry locator, unique selector
  evidence or editability oracle before proposing a new repair class.

Increasing a generic `max_rounds` is not a repair strategy. It must be replaced
by a named classification, edit surface, attempt cap, plateau rule, fixed-script
reproduction and non-matching control.

### 2. Case-library governance and campaign evidence

The case library is not an open hosted queue. `case.json`, registry, manifest,
split and admission/profile records govern whether a case is a development
oracle, counterexample, experimental record, future family candidate or
hosted-ready campaign member. M170 reuses three direct-evidence development
roles as a release gate; it does not promote the whole library. The later
selected milestone may qualify a separate frozen 30-case development denominator
only through its dedicated G2 case-and-reference workpack.

Case work supports the main objective in two ways:

- strengthen a later hosted denominator only by freezing an auditable family
  dossier, split, oracle, counterexample, gates and stopping rule; and
- fill a demonstrated mechanism or parameter gap when the terminal evidence
  identifies a missing observation, locator, oracle or discriminating control.

The five-family and parameter-variation plans remain useful **case-governance
and future campaign-design routes**. They are not the current default hosted
queue and cannot be revived by historical charter or report alone.

### 3. Reference experience projections

Development knowledge, human case cards, deterministic reference scripts,
development reference packs, runtime experience cards, tool schemas, IR and SDK
are distinct layers. Existing knowledge may be projected only through an
explicit, reviewed form with provenance, hashes, scope, counterexamples and
an evaluation plan.

For the current closed-loop release, experience enters only as one selected
hash-bound `vertical-cylinder-construction` card returned through the existing
tool bridge. The provider cannot enumerate, search, replace or choose card IDs;
the card is not default prompt injection and the case library is not RAG. The
later 30-case route must separately qualify every no-card/card disposition;
this release card does not automatically transfer to that cohort.

Future questions—whether compact cards help, whether bounded retrieval is
useful, or whether a stable SDK/IR surface is warranted—require separate
baseline/treatment or representation workpacks. They must not be mixed with a
repair-count experiment.

## Research-input interpretation

ReAct, Toolformer and RAG guide architecture rather than confer capability:

| Input | Useful design lesson here | Explicit non-claim |
|---|---|---|
| ReAct | Alternate bounded information actions with execution/gate feedback, preserving an auditable trajectory | No unrestricted agent, shell, or infinite reasoning/action loop |
| Toolformer | Typed APIs, argument validation, per-turn/request budgets and tool-result traces | No tool-use training or learned autonomous tool selection claim |
| RAG | Source/version provenance, hash binding, no-reference/reference ablation and leakage controls | No vector-store access to cases, automatic retrieval or broad repository context |

## Non-goals

This route does not authorize unbounded case expansion, generic retrieval,
automatic card promotion, prompt tuning after a result, model training,
unrestricted repair, held-out use, SDK/IR implementation, provider egress or
reuse of a historical report/budget/authorization.
